# 单 Agent 联动，切换走"卸旧装新"一次事务

收件目录 `agent/inbox/<phase>.jsonl` 里的事件**没有来源标识**，归一化层无法区分这条 `PreToolUse` 是 Qoder 还是别的 Agent 发的。
我们决定把"同一时刻只有一个 Agent 处于联动中"做成硬约束，并在插件页切换 Agent 时按**先卸旧、确认成功、再装新**的顺序交接，
失败则回滚到原状并在页面显示原因；而不是给事件加 `agentId` 字段做多来源归一。

**备选**：① 先装新再卸旧（没有"两边都没装"的空窗，但中间那一小段两个 Agent 同时往同一个 inbox 写，正是本卡要避免的）；
② 切换只改插件自己的状态、配置文件由用户手动装卸（零隐式副作用，但与"只开一个联动"的语义不一致，实际很容易两边都装着）。

**后果**：将来真要并行观测多个 Agent，就必须先给事件加来源字段并改归一化层，这是破坏性变更 —— 现在先不做，
因为单来源是用户明确要的语义。另有一条必须记住的代价：hook 装在别人的配置里时，**每一次**工具调用都会拉起一个
`desktop-pet.exe --pet-hook <phase>` 进程（分流在建窗之前），所以"停用/关闭联动"必须连带把条目剥掉，否则用户以为关了、进程还在被反复唤起。

## 补记（2026-10-18，A02）：来源字段加了，单 Agent 联动**定为长期路线**

本 ADR 开头的事实前提已经被改掉：从 A02 起，hook 命令串是
`"<exe>" --pet-hook <phase> --agent <id>`，收件 JSONL、`agent:state`、`agent:event`
**都带 `agent` 字段**，缺省（不带 `--agent` 的旧条目）按 `qoder` 处理。

**但结论没有变，而且不是因为来不及改。** 有了来源标识之后，理论上可以做多来源归一化，
我们仍然把「同一时间只有一个 Agent 处于联动中」定为长期路线，理由有三条，都是可验证的事实：

1. **多来源并不减少副作用，只增加副作用。** hook 装在别人的配置里时，每一次工具调用都会
   拉起一个 `desktop-pet.exe` 进程。同时挂四家就是四倍的进程、四倍的重复事件，
   而桌宠同一时刻只能演一个会话。
2. **归一化层缺的不是字段，是「该演谁」这个决定。** 两个 Agent 同时在跑时，宿主没有任何
   可靠依据判断用户此刻想看哪一个；把它做成自动仲裁，得到的行为是用户无法预期的。
   让用户在设置页明说（四选一）才是可解释的设计。
3. **单来源让「关掉」这件事有明确的物理含义**：停用插件 / 关闭联动 = 摘掉条目 = 不再唤起进程。
   多来源下还得定义「摘哪一家的、剩下来的算不算开着」，而这些状态宿主都观察不到。

于是来源字段的实际用途是**过滤与交接**，不是并行：

- watcher 逐行比对 `agent` 与 `agent-linkage.json` 里当前选中的那一位；不一致的行
  **只推进偏移量**，不进状态机、不广播。切过去的那一两秒里旧 Agent 还在路上的事件、
  卸旧失败的残余条目、用户手工拷过去的旧配置，都靠这条挡住。
- 切换仍按本 ADR 的**先卸旧、确认成功、再装新**；卸旧失败就停在原状态，绝不带着两份条目继续。
  命令是 `agent_linkage_set`，确认门（ZCode 的总开关）判在动任何文件之前。
- 切换成功要清空会话表：旧 Agent 的会话不该继续挂在状态卡上等 90 秒 TTL 才消失，
  那是「已经换人了还在演上一位」。

**新的代价**（要记住，别当成已经解决）：每家客户端的配置形状与总开关不同，适配器必须
**每次装卸都重新检测目录是否存在**（不能启动时缓存）；拨动过别人家的全局开关就得把原值记进
`agent-linkage.json` 并在卸载时如实恢复 —— 记不得就等于我们把用户的配置改坏了。
`--pet-hook-cleanup`（卸载应用前）按**每个已接线的适配器**各摘各的，不按「当前那一位」，
因为应用都没了，留在别人配置里的条目只会指向一个不存在的 exe。

## 补记（2026-10-18，A03：Codex 与 WorkBuddy 接线之后）

「同一时间只联动一个」这条不变量在四家之间长这样：

| 客户端 | 配置文件 | 事件数 | 超时键（单位） | 全局开关 | 我们对开关做什么 |
|---|---|---|---|---|---|
| Qoder | `~/.qoder*/settings.json` | 12 | `timeout`（秒） | 无 | — |
| ZCode | `~/.zcode/cli/{config,setting}.json` | 7 | `timeoutMs`（毫秒） | `hooks.enabled`（缺省即关） | **我们打开它**，装之前抄下原值、卸载时恢复 |
| Codex | `~/.codex/hooks.json` | 10 | `timeout`（秒） | 无 | — |
| WorkBuddy | `~/.workbuddy/settings.json` | 7 | `timeout`（秒） | `disableAllHooks`（**`true` = 全关**，语义与 ZCode 相反） | **不碰**。要用户自己去关这个键 |

两家开关语义相反是这张表里唯一真正危险的地方：如果宿主照 ZCode 那句「打开以后你之前配的 N 条也会一起生效」去问 WorkBuddy，就是在承诺一件我们不会做的事。所以确认框那句话归适配器自己说（`AgentAdapter::consent_prompt`），`[need-confirm]` 前缀仍是机器可读契约；而 WorkBuddy 的预检**排在卸旧之前** —— 预检如果晚了，症状恰好是本 ADR 最忌讳的那种状态：旧的已摘、新的没装，两边都不动。

### 残余风险（现在没解决，也别写成已解决）

1. **Codex 的 `config.toml` 我们既不读也不写**（A03 立项时定的边界）。代价是两种本该由宿主发现并说给用户的情况现在只存在于文档里：`config.toml` 里有内联 `[hooks]` 时，再写 `hooks.json` 会让 Codex 启动时告警（两边都会加载）；用户写了 `[features] hooks = false` 时整户 hook 是关着的。两种情形的表现都是「桌宠不动」，而我们的自检报 `null`（Codex 没有可查的日志），界面不会替用户诊断这个。
2. **Codex 的信任状态宿主观察不到**：非托管 hook 要在 `/hooks` 里审核并信任，信任绑在命令串的哈希上 —— 所以我们只能把这句话显示出来，无法知道用户到底信任了没有，也做不到方案 §3A 设想的「收到第一条事件之前一直显示等待信任」。那需要一个新的宿主状态，不在本卡范围。命令串因此保持稳定（只放安装目录下的 exe 路径 + 固定参数，不带版本号），否则用户每升一次版就要重新信任一次；dev 构建与安装版路径不同，各信任一次。
3. **WorkBuddy 桌面版没有官方 hook 文档**（设置页因此标「实验性」）。事件表只挂第三方实测会触发的 7 条；`SessionEnd`、`PostToolUseFailure` 等在 CodeBuddy CLI 文档里有、桌面版没实测过的，一律不装 —— 少装一条的表现是桌宠安静地缺一个状态，比报错更难查。它的 hook 配置在启动时缓存且关窗口不算退出，这句由 `post_install_hint()` 常驻显示。

## 补记（2026-10-28，G2-05：测试期路径覆盖变量怎么处理）

审计给的两个做法是二选一：① 要求显式总开关 `PET_AGENT_TEST_ISOLATION=1`；② 命中时输出 `override=`。
**选②：变量在所有构建里照旧生效，但凡是换了根的进程都要自己把它说出来。**

- 可见处：`agent_hooks_status` 的 `everywhere.overrides`（数组）、启动清理与 `--pet-hook-cleanup`
  的摘要行、安装自检的日志增量说明，都按同一份 `adapters::active_overrides()` 输出
  `override=<名字列表>`。设置页与 e2e 的隔离守卫读的是同一份回报，不再各自拼 env 去猜。

否决①的理由：总开关只是把「静默」从命中挪到未命中 —— 没设开关时变量失效、宿主静默退回真实
home，而那个方向的副作用恰好是本 ADR 要避免的「用户以为关了、我们却还在动他的配置」。
另一个方向（设了开关才覆盖）还会多出一处失败点：开关拼错、日志里没提示、配置被写到真实目录，
症状与 Bug1 同形。②的唯一代价是发布包里这些变量仍可被设置，但每个命中点都会留痕，
事后能追；这在「不可观测」与「可观测但需要人读」之间是更便宜的一侧。

对本 ADR 的直接后果：`everywhere` 回报的是宿主**实际**会读写的路径（含环境变量换根后的结果），
所以「同一时间只联动一个」「卸载要摘全部四家」这两条不变量在 e2e 里按这份回报判定，
不再让套件自己拼 env 去猜。

## 补记（2026-10-28，G2-09 复核 + G2-11：再启用的同意与无日志自检口径）

确认门（`[need-confirm]`）是「拨开用户总开关」的前置条件，只有**用户动作**能替用户同意：

- 用户在设置页重新勾选启用插件（`plugin_enabled_set`）视为对恢复总开关的同意 —— 停用时
  `uninstall_restoring_switch` 把开关还原成用户原来的 false，再启用必须能把它装回来，
  否则「停用→再启用」走一次就永久丢掉安装（G2-09 / t38-A）。
- 启动补写、启停清单迁移、插件目录扫描三条自动路径都不是用户动作，仍走严格确认门：
  需要确认的客户端拿到 `[need-confirm]` 报告，配置文件一个字都不动。

同时把无日志客户端的装后自检口径写实（G2-11）：`self_check` 对没有可查日志的客户端
（Codex / WorkBuddy）返回 `unverified` **对象**，`detail` 点明「该客户端没有可查日志」；
不是 `ok`（那是「查过且没问题」），也不是 `null`（那是旧契约，e2e 已按新口径改写）。
